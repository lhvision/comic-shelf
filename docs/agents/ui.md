# UI 设计与工程交付工作流（基于 Impeccable 核心方法论）

> **核心原则**：本项目所有涉及 UI/UX 的组件新建、页面重构、视觉打磨与交互变更，**必须严格执行本工作流**，杜绝 AI 审美向平庸均值回归（Slop），确保代码决策与物理落盘 100% 闭环。

---

## 一、核心认知（铁律）

1. **Slop 不是画功问题，而是向平均审美回归**：
   AI 产出“差一口气”的模板感，不是它画得不好，而是在没有明确约束时，它必然向训练数据里的高频答案做“平均审美回归”。换更强的模型只改变回归精度，不改变回归行为本身。
2. **Slop 有两层防线**：
   - **第一层：显性特征**（紫蓝渐变、渐变文字、毛玻璃、星星 icon、Unicode 伪字符……）——**黑名单与机器脚本能拦**。
   - **第二层：行为模式**（从“模板库”里挑一个套用）——**黑名单拦不住，必须通过“具体的约束 + 流程”逼出有辨识度的决策**。
3. **人是最终决策者**：AI 只做专业分析与执行，关键设计 Brief、视觉基调与重大取舍必须由人类确认。
4. **迭代式协作**：先给大方向，小步推进，一次只动一两个点。**严禁“一句 Prompt 吐出整个页面”**。

---

## 二、任务分级（防过度工程化）

在接到前端改动诉求时，Agent 必须首先判定任务量级：

- 🟢 **轻量级（单点修补/微调）**：
  - **场景**：修改已有样式的显性 Bug、微调 1~2 个 padding/margin/color token、修复文字溢出、调整 hover 态。
  - **处理方式**：直接读取现有设计 Token 执行最小必要修改，运行 `vp check` 与对应的精准单测，**豁免完整评审与快照流程**。
- 🟣 **探索级（即时变体探索）**：
  - **场景**：视觉概念未定、需对比多种版式方案，或用户明确提出“看看几种排版/设计变体”、“实时挑选视觉效果/动效”。
  - **处理方式**：在开发服务（`vpr dev:all` 或 `vp dev`）运行状态下切入 **Live 实时探索流**（定向变体 `/impeccable generate` 或全页拾取 `/impeccable live`），由人类在浏览器直观比对并拍板（Accept）。Accept 后**必须执行变体收敛清洗**（去临时 wrapper、样式 Token 化、`vpr detect:slop` 扫描）。局部排版探索豁免子代理快照，新建核心组件或视图级重构仍需在收敛后补齐子代理快照。
- 🔴 **重量级（结构性变更）**：
  - **场景**：新建组件（`src/components/*.vue`）、视图与路由级重构（`src/views/*.vue`）、核心交互与弹层体系演进。
  - **处理方式**：**必须完整执行以下实质性指令链**。

---

## 三、实质性指令链（SOP）

遇到 UI 任务时，Agent 依据任务分级具象推进：

> **Playbook 加载基准**：Agent 先找到 `impeccable` skill 的目录 `<impeccable-dir>`，在各步骤读取对应文档。

### 1. 对齐与约束：`/impeccable init`

- **真相源与基线**：改动前必须读取 `DESIGN_NOTES.md`（现状地图）与 `src/styles/tokens.css`；
- **反面参考最值钱**：牢记纸间绝对禁令（**严禁紫色渐变、严禁毛玻璃拟态、严禁第三方轮播、严禁伪字符**，统一朱砂点缀与物理纸本质感）；
- **模式判定（Register）**：纸间是个人私有收藏夹，设计为阅读与管理服务 → **Product 模式**（视觉隐身、严整装订感、信息与封面优先）。

### 2. 方案与底线：双轨起稿机制

在编写任何源码前，强制进入起稿关卡，根据场景选择分支：

- **分支 A（自主起稿：`/impeccable craft <target>`）**：
  - **强制加载底线规范**：必须先读取 `<impeccable-dir>/reference/craft-floor.md`（掌握触控尺寸底线、排版层级与对比度要求）；
  - **起稿前确认**：在对话中梳理：**设计 Brief → 布局基调 → 关键交互**，提出 2~3 个方向供人类确认，拍板后才起稿。
- **分支 B（即时探索：Live 变体模式）**：
  - **前置准备**：
    1. **开发服务与 HTTPS**：本地开发环境由 `basicSsl()` 原生提供 HTTPS（支撑 PWA 与安全凭据）。Live 模式必须在开发服务器（`vpr dev:all` 或 `vpr dev`，后端由 `vpr api` 支撑）运行下进行，浏览器直接打开 `https://localhost:5173/`（严禁在无 HMR 的 `vpr preview` 下运行）；
    2. **工程预设**：项目已预置 `.impeccable/live/config.json`（单页面 SPA `index.html` 入口），且 `.gitignore` 已排除会话日志与本地绝对路径；
  - **定向生成（优先推荐）**：已知目标元素时，执行：
    ```bash
    /impeccable generate 3 <action> <target-element>
    ```
    （例如 `/impeccable generate 3 bold "书架顶部筛选栏"`），由 Agent 定位元素并直接在浏览器内热替换呈现 3 种变体方案供人类比对切换；
  - **全页拾取（自由探索）**：需探索整个页面交互时，执行：
    ```bash
    /impeccable live
    ```
    开启长轮询与浏览器交互悬浮条，由人类在浏览器中点击 DOM 元素调出变体面板。
  - **Accept 后强制收敛（四步清洗铁律）**：
    人类在浏览器点击 Accept 或 Carbonize 后，Agent **绝不能**直接将临时内联代码作为最终成果，必须立即同步完成：
    1. **解构临时包裹**：清除 `data-impeccable-*` 属性、`carbonize` 外层 wrapper 及临时占位注释；
    2. **设计 Token 化**：将生成的临时内联 CSS 解构，颜色、间距、字体收敛进 `src/styles/tokens.css` 现有变量；
    3. **组件架构契约**：遵循纸间规范，单文件脚本不得臃肿（视图 ≤150 行，复杂状态下沉至 `src/composables/`）；
    4. **机器规则扫描**：运行 `vpr detect:slop <target>`，确保零显性 Slop。
    - **门禁衔接**：若是已有组件的局部排版/样式微调，单测验证通过后即可交付；若是新建组件或视图重构，进入 Step 3 补齐子代理快照。

### 3. 双轨隔离挑刺：`/impeccable critique <target>`

利用“AI 挑刺别人的能力远强于自我审查”的特性，**必须物理隔离评审上下文**：

- **A 轨（主观·独立设计总监）**：
  - **必须派一个独立子代理（独立上下文）评审**（角色：`Design Director`）；
  - **子代理派发指令契约**：Prompt 中必须显式要求：_“请先读取 `<impeccable-dir>/reference/critique.md`，严格按照其 10 项 Nielsen 可用性评分标准与认知负荷检测逻辑审查目标代码，必须挑出至少 1~2 项实质性 P1 缺陷，严禁全打满分（40/40）的虚假汇报”_；
- **B 轨（客观·机器规则扫描）**：
  - 必须在终端运行 `vpr detect:slop <target-file>`，通过确定性规则扫描排除显性 Slop 与格式漏洞；
- **分级归类**：整理为 **P0（阻断）/ P1（缺陷）/ P2（体验）** 清单；刻意保留的取舍写进 `.impeccable/critique/ignore.md`。

### 4. 照单系统修复：`/impeccable polish <target>`

- **加载打磨规范**：可查阅 `<impeccable-dir>/reference/polish.md`；
- **消除缺陷**：直接将 Critique 产出的 P1 缺陷清单作为待办，在源码中逐项消减修复；
- **精准单测验证**：运行针对该组件的精准单测（如 `vp test src/__tests__/<Target>.spec.ts`）确保功能自愈。

### 5. 响应式适配与双轨落盘：`/impeccable adapt <target>`

- **多端与动效适配**：查阅 `<impeccable-dir>/reference/adapt.md`，处理小屏幕响应式断点（`<=681px` 窄屏折行、触控尺寸 ≥ 44px）与 `prefers-reduced-motion`；
- **产物双轨落盘铁律（必须物理分开）**：
  1. **评审快照（事实痕迹）**：运行项目便携命令落盘至 `.impeccable/critique/`，**只追加不覆盖**：
     ```bash
     vpr critique write <slug> <critique-report.md>
     ```
  2. **现状地图（最新真理）**：若涉及**设计 Token 演进、核心组件变体（如 Modal 变体）、破坏性视觉规范变更或新增全局交互隐喻**，提炼并更新 `DESIGN_NOTES.md`（常青设计系统规范）；单次评审细节由 `.impeccable/critique/` 快照承载，避免历史流水账无节制堆叠；
  3. **严禁混写**：重写决策会污染历史，快照只记录当次评审，设计系统规范只记录当前真实基准与通用定律。

## 四、防形式主义自检红线（Anti-Slop Redlines）

Agent 在声明任务完成前，必须核对以下红线：

1. **严禁口头走流程**：对话里写了“我执行了 Impeccable”，但 `.impeccable/critique/` 没生成文件的，判定为任务未完成（豁免快照的局部微调任务除外）；
2. **严禁自导自演假评审**：Critique 阶段必须派一个独立子代理（独立上下文）评审，严禁在同一会话中自己量自己的尺子；
3. **严禁无瑕疵满分快照**：全新或重构组件若出现 40/40 满分且无任何 P1 待办，判定为敷衍应付；
4. **严禁绝对系统路径**：落盘与检测工具必须走 `vpr critique write` / `vpr detect:slop` 跨平台代理，严禁硬编码本机路径；
5. **严禁 Live 临时污染残留（Clean Exit）**：任务结束或提交前必须核对 `git diff`，严禁将任何包含 `data-impeccable-*` 属性、`impeccable-variants-*` 占位注释或 `live.js` 脚本注入残留带入源码库；若 Live 流程异常中断，必须手动或执行自愈清理至零污染。
