# OCRia-nano-1 对纸间的适用性评估

核查日期：2026-11-25。状态：已完成首轮真实画页对比与方向处理复核；建议保留现有默认引擎，未修改生产实现。

**这两个候选中，纸间当前应继续使用 RapidOCR + PP-OCRv6 small。** OCRia-nano-1 在样本对比中确实更快，但通过 LiteParse 2.21.1 处理简中、繁中、日文竖排漫画时出现了乱码和整页漏识。决定默认方案的主要依据仍是能否提取出可检索的对白。

这次结论针对 `ocria-nano@1.0.0`、LiteParse `2.21.1` 和现有混排漫画语料，不代表 OCRia 对普通横排文档无用，也不证明未来版本或另行实现的竖排适配会得到相同结果。当前没有增加第二引擎、自动降级或新的生产依赖。

## 本地画页对比

原始评测记录包含运行环境、藏书路径、参考对白、图片哈希和逐页推理输出，仅作私有归档，由 Git 忽略，不随仓库提交。本说明保留验证方法、对白核验汇总与选型结论；设备型号、系统环境、路径和具体耗时及内存数据不在此列出。评测没有改写书库中的伴生资产或 SQLite。

### 输入与测量口径

- 两个引擎在相同计算条件下，分别以独立进程顺序执行，使用相同的单核预算和一个 worker。RapidOCR 明确设置 ONNX Runtime 单线程、关闭 CUDA，并核验三个推理会话均为 `CPUExecutionProvider`。
- 共 11 页：7 页用于参考对白核验，另有广告、前言和无对白插画等对照。7 页中包含简中竖排、繁中竖排、日文竖排和日文横排小字；部分页来自同一作品或同一画面的不同汉化版本，不能当作独立随机样本。
- 两个引擎读取相同的 EXIF 校正、RGB PNG 副本，采用现有 `cluster_blocks` 归整。RapidOCR 使用 v6 small、`Global.text_score=0.5`；LiteParse 指定 `ocr_backend=ocria-nano`、`dpi=250`，保留小字与页眉页脚，遇到解析错误要求失败。
- 每个进程先预热一页，再运行 11 页两轮。计时包括图片解码、推理、文字适配和气泡聚类，排除模型初始化、原图转 PNG、伴生写盘和索引同步。进程峰值 RSS 包含依赖、缓存与积累的评测结果，并非模型独占内存。

### 完整对白核验

对 7 页的 19 条参考对白直接查看原图转录并再次核验。其中 18 条竖排、1 条横排。匹配先做 NFKC 归一，再忽略标点与空白；参考原文须作为单个聚类气泡中的连续子串出现。气泡多出文字不扣分，因此该指标是局部完整提取检查，**不是全页字符准确率、全库召回率或气泡分组正确率**。参考由代理视觉核验，尚未经独立人类复核。

| 局部参考检查               | PP-OCRv6 small | OCRia-nano-1 |
| -------------------------- | -------------: | -----------: |
| 18 条竖排对白完整匹配      |        17 / 18 |       0 / 18 |
| 1 条日文横排长对白完整匹配 |          1 / 1 |        0 / 1 |
| 合计                       |        18 / 19 |       0 / 19 |

OCRia 的横排长对白并非完全不可读：它基本提取出了整段原文，但有一个汉字识别错误，因此没有通过完整匹配。竖排的失败则包含明显乱码及完全漏识，不能用这一横排单字错误概括。

逐页核验发现：

- 一页有三段清晰日文竖排参考对白：v6 均能完整提取，OCRia 两轮均返回 **0 条文字项**，且没有报告解析异常。
- 同一画面的简中与繁中版本：v6 能提取所选完整对白，OCRia 多段变成中、日、韩字符混杂的乱码。另有一处人工参考转录已按原图纠正，避免用错误参考惩罚模型。
- 另一页日文竖排对白：v6 也漏了句首几个字；保留默认引擎不等于它没有漏识。

### 耗时与内存

稳态统计各取 22 次逐页执行，OCRia 的耗时与评测进程峰值内存均更低。重复测试中的耗时存在波动，不能据此承诺目标部署环境或正式批处理的性能。具体测量值仅保存在私有评测记录中。

两个引擎均没有报告解析异常，但零异常不等于零失败，有字页返回空结果正是这次发现的质量问题。

模型初始化与首次解析单独保存在记录中；未保证磁盘冷缓存，不能把它们作为严格冷启动基准。本次没有测 GPU，也没有完成端到端写盘或索引吞吐测量。

### 漏识与方向处理复核

针对日文零文字页、简中竖排页和日文横排对照，共做了 15 次附加解析：分别显式传入零度页面纠正、关闭扫描去噪、改为 `dpi=150`、将输入旋转 90° 和 270°。这些变体都没有恢复所选竖排对白；旋转后零文字页有时返回文字项，但内容仍是乱码。零度页面纠正也没有阻止简中页的输出宽高交换，不能把这个配置当作关闭所有自动方向处理的开关。

核对同一上游源码版本发现，[`page.rs`](https://github.com/run-llama/liteparse/blob/b2ca8f00e8c0b8e78c4e40bd0c2a60ce9d48f3f2/crates/liteparse/src/ocr/ocria/page.rs) 的 `crop` 会把高宽比至少 1.5 的竖长框旋转为横条；[`mod.rs`](https://github.com/run-llama/liteparse/blob/b2ca8f00e8c0b8e78c4e40bd0c2a60ce9d48f3f2/crates/liteparse/src/ocr/ocria/mod.rs) 还会重试看似横倒的整页，再由路由器选择文字体系和翻转方向。这是文档扫描件的处理路径；本次尚未证明其中哪一步单独造成漫画漏识，不能直接归因于字符表或某一项参数。

有些竖排输入经 LiteParse 后页面宽高交换，文字坐标位于处理后的页面空间。初步适配仅按输出宽高归一，没有逆旋转；**这些页的聚类框不能作为原图定位或阅读顺序质量的依据**。文字项本身已含乱码或为空，坐标修正不会补回缺失的原文。若以后重新评估，需要同时解决竖排字形识别、检测、方向和坐标回映射，不能只替换一行引擎初始化。

另有一个包装层问题：LiteParse 2.21.1 的 `get_config()` 访问原生配置缺少的 `keep_clipped_text` 字段而抛出 `AttributeError`。评测将其记录后直接读取已存在的原生配置字段，实际 `parse()` 可运行；这不是上述零文字页的原因。

## 官方同流水线比较

纸间的 [OCR worker](../scripts/ocr_worker.py) 使用 RapidOCR 3.x + **PP-OCRv6 small**，支持 CPU 和显式验证过的 CUDA 推理。模型固定 small 的原因是项目需要简中、繁中与日文覆盖。

技术报告表 5、表 6 在同一 LiteParse + LayoutNet 流水线内替换 OCR 后得到：

| 指标                  | OCRia-nano-1 | PP-OCRv6 small |
| --------------------- | -----------: | -------------: |
| ParseBench-2 总分     |         59.2 |           59.9 |
| ParseBench-2 文字分   |         68.5 |           71.9 |
| 单核平均延迟          |    426 ms/页 |    1,963 ms/页 |
| 单核 P90 延迟         |    862 ms/页 |    4,988 ms/页 |
| 16 个单核 worker 吞吐 |   27.8 页/秒 |      5.7 页/秒 |

这支持“CPU 速度更快、文字质量有取舍”的判断，不能据原帖概括为比纸间现有引擎更准确。文字分也不是字符准确率。

测速使用 300 张随机 ParseBench 文档页，包含原生文字 PDF 和扫描件；PP-OCRv6 通过 RapidOCR HTTP 服务接入。纸间直接处理光栅漫画画页，另有聚类和伴生写盘，两者工作负载不同。报告的约 4.8 倍吞吐不能直接作为纸间或 NAS 的加速预期，也未与项目 GPU 路径比较。

[现有部署文档](../DEPLOYMENT.md)说明了 CPU 与 GPU 的运行方式。实际画页提取还包含聚类和伴生写盘，不能直接套用官方文档页基准，应在目标部署环境按真实工作负载验证。

## 适用范围

| 纸间需求                   | 适配判断               | 依据与待验证项                                                   |
| -------------------------- | ---------------------- | ---------------------------------------------------------------- |
| CPU 批量画页文字提取       | 有提速，但不宜默认替换 | 本地样本耗时更低；竖排对白漏识与乱码使其无法替代当前默认方案     |
| 简中、繁中、日文混排       | 当前竖排样本不合格     | 声明支持 CJK，但实测横排与竖排表现差异明显                       |
| 台词全文检索、语义召回     | 可复用现有下游         | 经适配生成伴生资产后，继续由现有索引同步处理                     |
| 阅读器气泡定位             | 需要输出适配           | 文字行须聚类为气泡；自动旋转页还须做坐标逆变换，尚未通过定位核验 |
| 在线画页翻译               | 可提供识别原文         | 模型没有翻译能力；触发入口、执行位置、译文保存和绑定需要另定     |
| 以图搜图、分镜与说话人识别 | 没有直接对应能力       | 文档布局类别不等同于漫画分镜、气泡或角色归属                     |

模型整体含七个组件，共 8.1M 参数，其中 OCR 检测、路由与四个识别器约 3.9M，LayoutNet 约 4.27M。LayoutNet 的文档表格和布局能力未证明能改善漫画气泡整理。

## 将来重新评估时的接入位置

本次不接入第二引擎。若后续版本解决漫画竖排问题，可沿用 [ADR 0041](./adr/0041-ocr-file-extraction-boundary.md) 的文件提取与本机同步边界：

`画页 → LiteParse/OCRia 文字项 → 现有气泡聚类及阅读排序 → .ocr.json → 本机同步 → 台词检索`

1. 试验先使用独立画页副本与输出目录，保存两个引擎的原始文字项和聚类结果，供逐串对比。
2. LiteParse JSON 的文字项坐标使用左上角原点的页面坐标空间。转换为现有 `[ymin, xmin, ymax, xmax]` 时，按同一空间的页面宽高归一，并核对图片转换、EXIF 方向和旋转后的对齐。
3. 尝试复用 worker 的 `cluster_blocks` 和 `sort_bubbles_by_reading_order`，验证新检测框的粒度是否适合现有聚类。官方文档段落框不能直接当作台词气泡框。
4. 按 [伴生校验](../backend/app/ocr/assets.py) 保存原图状态、引擎、模型版本及提取配置。现有 worker 的缓存检查固定要求 `engine=rapidocr`，正式接入时需要处理新引擎身份和混跑新鲜度。
5. 下游复用现有分类、全局页码映射、关键词索引和可选向量编码。SQLite 仍由数据库所属主机本地同步。

LiteParse 提供 Python 绑定；PyPI `2.21.1` 声明 Python ≥3.10，并提供 `cp310-abi3` 的主要平台 wheel。本次已验证其 Python 绑定可在项目要求的 Python 3.14 下安装和运行，未加入项目依赖。模型卡要求通过 LiteParse 使用这些模型文件。

官方报告的模型加 ONNX Runtime 安装占用为 Linux 59.9 MB、macOS 75.3 MB。这个数字不含全部 LiteParse/PDFium 安装开销，也不是运行内存峰值。模型可提前下载、校验哈希并离线运行；运行阶段无需云端解析请求。

## 授权边界

LiteParse 代码为 Apache-2.0。OCRia-nano-1 权重及模型仓库附带的部分配置/代码为修改后的 Open RAIL-M，带使用限制，不能整体当作无条件开源依赖。

- 原文允许个人使用与评测、研究，包括发布评测结果。
- 对超过 200 万美元收入或融资门槛的非豁免使用，以及构成竞争性文档解析/OCR 服务的使用，另有授权要求。
- 模型分发有许可证、归属及限制传递要求；默认打包进纸间发布物需单独核对具体分发方式。通过独立进程调用也不会取消模型自身的使用限制。

因此，个人书库样本评测具备明确的授权入口；项目采用 AGPL-3.0 并不能代替模型自身的许可。是否纳入默认发布物尚未决定。

## 后续取舍

当前保留 v6 small，无需先引入双引擎或按置信度回退。OCRia 这轮返回的部分乱码仍有较高置信度，置信度不能可靠地决定是否需要回退；全文与语义索引都无法补回根本没有提取出的对白。

如果之后出现支持漫画竖排的新版本或明确适配，再以这些失败页做回归起点，扩到约 40 页，补齐独立人类真值、字符错误、跨气泡误并、框位置、阅读顺序及真实检索召回；随后测目标 NAS、CPU 核数预算和端到端写盘。当前样本已足以否定所测试组合直接作为默认替代，无需先跑全库才能作出这一建议。

[踩坑记录 #143](./PITFALLS.md) 已记录现有 GPU 链路的提速尝试与逐串核验要求；[生态路线图](./AI_ECOSYSTEM_ROADMAP.md) 记录 v6 质量达标结案。这些是历史验证记录，不能用于推断生产环境的实际数据状态。当前生产镜像与依赖保持原状。
