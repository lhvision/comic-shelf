# ADR 0017 — 漫画台词全文检索（SQLite FTS5 + Trigram）与阅读器气泡呼吸高亮定位架构

- **日期**：2026-09-12
- **状态**：Accepted
- **关联**：扩充 `CONTEXT.md`「台词全文检索 (FTS5)」「气泡呼吸高亮」「伴生资产协议」，演进 `DESIGN_NOTES.md` §62，关联 `docs/PITFALLS.md` 避坑条目 79 与 80，落地 `docs/AI_ECOSYSTEM_ROADMAP.md` 阶段一先行项

## 背景

在纸间（Paper Room）的日常使用中，读者经常面临“记得经典对白或名台词，但遗忘了具体本子或出处画页”的检索痛点。同时，随着未来多模态与 AI 演进路线（AI 漫画创作、二次元专精翻译微调、2D 互动 AVG 游戏）的确立，对画页分镜内的文字及对白气泡进行结构化感知与索引已成为核心基建。

此前，纸间主要依赖基于标签、标题的元数据检索以及基于特征向量的以图搜图（`imsearch`），缺乏细粒度的文本对白检索能力。引入台词全文检索面临以下技术挑战与边界约束：

1. **中日文混合分词与轻量化**：不能引入庞大的第三方分词服务或重型 Python 分词包（如 jieba 词库），必须保持极速、轻量与本地化；
2. **简繁双向互通**：汉化组对白多为繁体，而读者多以简体检索，必须解决简繁异体字造成的召回断层；
3. **伴生资产协议解耦**：OCR 解析与气泡提取属于计算密集型任务，必须与读者端解耦，确立 `{index}.ocr.json` 伴生资产契约；
4. **多章节全局页码对齐**：纸间阅读器与对外 API 全面采用全书拍平的全局页码（1..`page_count`），伴生文件按章节物理分片存放时必须严格映射为全局单调递增页号；
5. **幽灵索引与隐私防线**：漫画删除、重装或设为访客隐藏（`hidden_from_guest`）时，严禁向未授权用户或外部接口泄露台词内容；
6. **前端气泡定位与视口漂移**：不同屏幕尺寸与长宽比下，图片居中常产生可变的留黑边缘（Letterbox / Pillarbox），气泡高亮框必须绝对贴合实际画面，且不能阻塞任何交互。

## 方案论证与权衡（Grilling Analysis）

围绕存储选型、简繁转换、坐标契约与前端动效渲染，团队展开了针对性推演：

### 1. 检索存储与分词选型

- **路线 A（外部向量数据库或专用搜索引擎 ES/MeiliSearch）**：
  - _否决理由_：违背纸间“本地优先、极简单机、低功耗”的原则，额外引入后台常驻进程与内存开销。
- **路线 B（SQLite LIKE / 正则匹配）**：
  - _否决理由_：全表扫描性能随台词量线性劣化，无法实现高效倒排索引与词元打分。
- **路线 C（SQLite FTS5 + Trigram 分词，推荐）**：
  - _实现原理_：利用 SQLite 内置的全文检索模块 FTS5，采用 `tokenize='trigram'`（三元语法分词）。
  - _技术优势_：原生内置 0 额外依赖；Trigram 对中日韩无空格文本具有天然的任意子串模糊匹配优势，且内存占用极低、响应在毫秒级。

### 2. 简繁异体字处理

- **路线 A（引入 opencc-python 依赖库）**：
  - _否决理由_：需要编译 C++ 扩展或拉取重型字典包，增加 Docker 与各平台移植成本。
- **路线 B（零依赖 OpenCC 精简双向映射字典，推荐）**：
  - _实现原理_：编写 `backend/app/zh_conv.py`，提取 3,881 对最高频中日汉字简繁对应表（数据解耦存储于 `backend/app/assets/zh_tables.dat` 压缩二进制资产并惰性单例加载，消除源码巨型字面量对 IDE/LSP 的解析卡顿），在搜索入参层进行变体展开（`expand_search_variants`），生成 `(term_simp OR term_trad)` 查询原语，保持零外部依赖且覆盖 99.9% 二次元对白场景。
- **修订（2026-09-23，台词出口由查询侧改为索引侧归一）**：路线 B 的字典与零依赖前提保留，**改变的是归一发生的位置**。真库 7544 条台词里有 1238 行含繁体字形，其中 **735 行（59%）用简体照着页面打出来搜不到**——因为映射是逐字符一对一，一次查询最多产出「原样 / 全简 / 全繁」三个**整串**写法，而汉化组语料大量是**同一行内繁简混排**（嵌字只换了一半、字体缺字）：语料「縮紧」，查询「缩紧」展开成「缩紧」与「縮緊」，两个都不等于它。现方案给 `comic_dialogues_fts` 增列 `text_norm`，写入时即 `to_simplified(text)`，**倒排只建在这一列**；查询侧只做一次 `to_simplified`，单条 MATCH，不再展开变体。`text` 退为 UNINDEXED 的原文副本：展示与 `<mark>` 高亮仍用页面上那套字形（1:1 映射保证字符偏移可直接回切，`_make_snippet` 在归一列定位、在原文上切片）。缺列即触发既有整表重建 + 回填，无需人工迁移。收益实测：那 735 行 100% 可被简体命中，繁体原文照抄与日文行照抄检索均无回归（108/108）。书架元数据出口**不变**，仍是查询侧多组 `LIKE` OR。

### 3. 伴生资产契约与多章节全局映射

- **契约规范**：每个画页伴生 `{index}.ocr.json`，内含 `bubbles: [{ id, order, box: [ymin, xmin, ymax, xmax], text, confidence }]`（`order` 为 2026-09-22 增补，见「核心决策」第 6 条）；
- **百分比归一化坐标**：`box` 采用 `[0.0, 1.0]` 浮点百分比，与原始图像像素尺寸完全解耦，缩放或转换 WebP 无需重算；
- **全书平铺单调递增映射**：`sync_comic_dialogues` 遍历多章节目录时，严格按照全书目录章节顺序累加基准偏移（`offset`），将章节内局部页码映射为全书全局页码，彻底杜绝切话阅读器页码跳跃错位。

### 4. 访客隔离与幽灵索引防线

- **幽灵索引原子清理**：在漫画画页重新装订（`replace_comic_pages`）或整本删除（`delete_comic`）时，事务内执行 `DELETE FROM comic_dialogues_fts WHERE source = ? AND source_id = ?`，杜绝孤儿索引。
- **访客权限双重判定**：在检索 SQL 中绑定 `:is_not_guest OR (ci.source IS NOT NULL AND COALESCE(ci.hidden_from_guest, 0) = 0)`，并联合 `comic_info` 校验，孤儿记录或访客隐藏本子绝对不向访客与未授权 API 泄露。
- **沙箱穿越防御**：所有 OCR 文件与目录解析必须经过 `cand_resolved.is_relative_to(data_resolved)` 物理边界断言。

### 5. 前端气泡定位与视口抗漂移架构

- **Aspect-Ratio Lock（宽高比锁定帧）**：气泡高亮层（`ReaderBubbleOverlay.vue`）置于与图像等比的 `.comic-page-img-frame` 内；底图解码后动态注入 `aspectRatio: naturalRatio`，翻页模式（`vertical-paged` / `horizontal`）与自适应高度模式下 `img` 设为 `width: 100%; height: 100%`，根除 Flex 百分比高度计算失效导致的图片膨胀溢出与 Letterbox 黑边位移，实现跨全模式与视口尺寸 `diff(img, frame) === 0` 绝对贴紧；
- **全模式图片适配显式约束**：设置面板对图片适配选项全模式常驻，在翻页模式（`vertical-paged` / `horizontal`）呈置灰锁定态，展示胶囊徽标 `〔 翻页已锁定整页入目 〕`，坚守离散翻页“一次一屏”契约并消除选项丢失困惑；
- **刚性吸附手感（Mandatory Snap）**：竖向翻页升级为 `scroll-snap-type: y mandatory`，与横向翻页一致，消除因弱吸附造成的伪连续滑移；
- **坐标标度自适应防溢出**：`parseBubbleBox` 智能探测 OCR 0..1000 标度与百分比标度并自适应降阶至 [0.0, 1.0]，顶部分镜微标胶囊自适应翻转至下方，右侧分镜靠右对齐；
- **图片就绪门禁（`imageReady`）**：监听图像解码完成事件，图片就绪后才激活 2.2 秒呼吸动画，防止骨架屏遮挡动画；
- **交互与无障碍**：采用 `pointer-events: none` 零阻碍主阅读手势与翻页，并针对 `prefers-reduced-motion` 自动降级为静态淡雅半透明金框。

### 6. 前台书架搜索栏联想浮层与交互架构

- **双重搜索意图解耦（静默伴生原则）**：书架主输入框承载「标题/车号/作者/标签」与「分镜台词全文检索」。为避免干扰读者日常淘书心智，台词自动检索在命中 0 条时**严格保持静默隐藏**，绝不弹出侵入性空状态弹窗遮挡已过滤漫画；仅当命中台词或读者主动按 `ArrowDown` 显式探寻时展开浮层；
- **纯声明式分镜高亮（零 XSS）**：后端 FTS5 返回的 `<mark>` 高亮片段通过手写 `parseSnippetTokens` 解析为结构化 Token 数组，在 Vue 模板中声明式渲染，彻底杜绝 `v-html` 注入风险；
- **WAI-ARIA Combobox 与视口对齐**：完整实现 `role="combobox"`、`aria-controls`、`aria-activedescendant` 标准无障碍契约；键盘上下方向键导航时监听 `focusedIndex` 执行 `scrollIntoView`，杜绝长列表盲航；智能回车兜底直达第 1 项最优分镜。

## 核心决策

1. **底层存储**：在 SQLite 初始化 `comic_dialogues_fts`（Trigram 分词），收录 `(source, source_id, page_index, bubble_id, text, lang, box_json, reading_order, kind)`——除 `text` 外全部 `UNINDEXED`，`kind` 追加在列尾以保住 `snippet(..., 4, ...)` 的列号；
2. **同步管线**：提供 API `POST /api/library/{source}/{source_id}/ocr/sync`（Machine Token / Curator 鉴权）与离线 CLI `scripts/sync_ocr.py`（支持 NAS 挂载检测与多进程同步）；
3. **检索端点**：提供 `GET /api/search/dialogue`，支持简繁多词元展开、长度上限 200 字符限制与访客权限隔离；
4. **前端响应与排版规约**：阅读器支持 `?page=42&bubble_box=...`（代表格）、`?page=42&bubble_boxes=a;b;c`（同页其余命中格，`;` 分隔）、`bubble_text` 与 `?page=42&highlight_bubble=1` 参数直达并呼吸高亮；全阅读模式统一收敛至 Aspect-Ratio Lock 几何贴紧，翻页模式锁定整屏入目与刚性吸附；
5. **前台书架集成**：在 `LibraryView.vue` 搜索栏接入 `DialogueSearchPopover.vue`，基于静默伴生原则消除意图冲突，纯函数声明式高亮杜绝 XSS，WAI-ARIA Combobox 标准与 `scrollIntoView` 视口跟随对齐。
6. **页内阅读顺序显式化（2026-09-22 增补）**：`cluster_blocks` 原先只排每个气泡内部的文字行，气泡之间的次序沿用 OCR 检测模型输出，页级顺序既不稳定也未落库。现由 `sort_bubbles_by_reading_order` 补齐页级排序（竖排页自右向左分栏、横排页自上而下分行，扫描轴重叠者并入同栏），写入侧落 `order`、入库侧落 `comic_dialogues_fts.reading_order`，下游以 `(page_index, reading_order)` 还原整话台词流。`id` 与 `order` 分成两个字段，顺序规则日后调整不牵连气泡身份。FTS5 虚拟表不支持 `ALTER TABLE ADD COLUMN`，新增列只能在 `init_dialogue_db` 内 drop 重建，并必须同步清空 `comic_ocr_sync_meta`——否则 mtime 增量判断会认为「已同步」而跳过重灌，台词检索从此永久返回空集。
7. **语料分类在入库侧而非 OCR 侧（2026-09-22 增补）**：汉化组 credits、招聘广告、社媒链接、活动 logo 与作者后记混在台词里，既污染检索结果又虚增页级命中数。曾评估过"漫画对话在文本框内、后记与封面标题不在"的几何判据，用 `cv2` 对 501 条已入库语料做了只读探针（两套内腔/描边判据 × 四种阈值）：**脏数据 16~17/17 命中，但真台词误伤 41%**——气泡内腔常与整页白底漏成同一个连通域，而矩形旁白框、书页外框同样是闭合轮廓，几何上无法与气泡区分，故弃用。改用纯文本与页码可得的三条规则（前 2 页 / 末 4 页带整页护栏 / 特征词与"无中日文字形且 ≤12 字符"），实测脏数据 17/17 命中、真台词仅 1 条被误判。分类落在 `sync_comic_dialogues`（`classify_dialogue_kind`）而非 `ocr_worker.py`，三条理由：① 伴生文件里硬编码的 `"type": "dialogue"` 后端从未读取，为它重跑 99 页 OCR 毫无收益；② 侧车应当只记录 OCR 看见了什么，"这条算不算台词"是检索策略，随策略调整只需重灌、不需重识别；③ 判定需要全书 `page_count`，`album.json` 在入库侧本就已加载。产物是 `kind` 列（`dialogue` / `paratext`）：副文本**保留在索引内**供后续取料出口与语义召回使用，只是不再出现在台词检索里；水印与页码属纯噪声，直接不入库（501 → 465 行）。**2026-09-22 修正一处判据**：尾页护栏原本写成"整页有任何一行是特征词**或噪声**即判副文本"，而噪声行在函数开头就已经单独 `return None` 不入库了——它不该再有替整页定性的权力，正文页上同样满是水印。真库实测这个 `or _is_noise_line` 分支误杀 60 页剧情尾页 / 119 行台词（例：jm/319445 p21 只因侧车里有一行把 `？？？` 认成 `888` 的噪声，整页从台词检索里消失，而那页正是剧情收尾）。现改为**只认特征词**；重灌（`scripts/sync_ocr.py --force`，不重跑 OCR）后 dialogue 7139 → 7258、paratext 637 → 518。
8. **一份索引、两个出口（2026-09-22 增补）**：同一份 `comic_dialogues_fts` 上长出两条方向相反的出口。人用出口 `search_dialogues` 要 bm25 相关度、要 `<mark>` 高亮、要压成 20 页给人眼挑；管线出口 `get_story_context`（MCP 工具同名，另有 `GET /api/search/dialogue-context` 供前端与脚本调用，仅馆长与 Machine Token 可用）反过来——**不收关键词**、**不吐展示态字段**、按 `(page_index, reading_order)` 的剧情原序给连续切片、行数由 `budget_lines` 预算决定而不是由相关度决定，撞预算必须回报 `truncated`（否则模型会把自己拿到的片段当成全书）。返回拆成 `lines`（给模型：`line_id`/页码/序号/纯文本）与 `boxes`（给渲染层：`line_id` → 四点坐标）两份，靠 `line_id` 关联：气泡坐标是画在原图上的，塞进 prompt 只会成为噪声。区间上限 `STORY_CONTEXT_MAX_PAGES = 200` / `STORY_CONTEXT_MAX_LINES = 400` 是硬天花板，防"整本书一把梭"。两条已知限制写在这里，避免下游踩到时才发现：① **不输出 `speaker` 字段**；② **`reading_order` 是稳定序号而非连号**——2C 之后噪声行不入库，同页序号会出现空洞（实测 `1,2,3,4,5,7,8`），下游不得用序号连续性判断是否缺行。
9. **截断留谁由相关度 + 业务信号共同决定（2026-09-22 增补）**：语料到 7776 行 / 43 本之后，`老师`、`喜欢` 这类常用词必定顶到页坑位上限，此时"谁被截掉"才是用户实际看到的排序质量。实测证据：`老师` 候选池 100 页里**前 20 名的相关度全部打平在 1.0**（2 字走 `LIKE`，`词频 ÷ 文本长度` 是个很粗的比值，一堆气泡算出同一个数），截断等于由 `(source, page_index)` 的偶然次序决定。故 `search_dialogues` 在页级聚合之后追加一层融合：`rank_score`（**候选池内** min-max 归一到 0..1 的纯相关度，两条检索路径先统一成"越大越相关"再归一）＋ 四类业务信号——热度（`views`/`likes` 取 `log10(1+n)` 相加，在**本次池内出现的那些书**之间 min-max）、收藏（0/1）、完读率（`last_page / page_count`）、最近阅读（30 天线性衰减），权重 `0.15/0.15/0.10/0.10`。三条刻意的约束：① 信号**只抬升不压低**且合计封顶 0.5，所以相关度差 0.5 以上翻不了盘（实测四项全开的 0 分长句仍排在无信号的 1.0 短句之后），不会出现"为了个性化把不相关的顶到第一"；② 无信号（未登录视角、本地导入本、从没读过的书）时抬升恒为 0，顺序自动退回纯相关度，不需要任何分支；③ **只有顺序随身份变**，`bubble_count`/`rank_score`/`text` 这些字段在同一页上必须逐字一致（真库 95 页交集实测 0 处不一致，单测 `test_dialogue_business_signal_ranking` 锁死），这条是错题本 #139「计数类字段不得按身份分档」的延续。附带两条落地口径：`comics_index.views`/`likes` 是上游站点的**展示字符串**（实测形态只有 `''`、`102`、`9K`/`99k`、`999K`、`9.9M`），`_parse_metric_count` 认不出的回报 `None` 而非 `0`——空串是"这个源没有热度"，当成 0 阅读量等于替本地导入的本子编一个；`rank_score` 语义固定为**纯相关度**，不把融合分混进去，日后调权重不改变已下发字段的含义。

### `speaker` 为什么决定不做（2026-09-22，附实测）

取料出口要 `speaker`，但仓库里没有这个信息。三条免费/低成本路径全部实测走不通：

- **短行即说话人标签**：全库 433 条台词里 `≤6 字且无句读` 的有 131 条，逐条读下来几乎全是**真台词或拟声词**（`好可爱`、`没事`、`看招`、`非常抱歉`、`小穴夹得好紧`），不是"未花："这种署名；
- **`album.json` 的 `actors` 当白名单**：里面是**全名与系列名**（`圣园未花`、`桐藤渚`、`Blue-Archive`），而对话里用的是简称（`未花`、`渚`、`老师`、`圣娅`），131 条候选对 `actors` **零命中**；
- **句内「名字：台词」前缀式**：全书只搜到 1 条，且那句是两句粘连（`毕竟：这次怎么说得出口`），不是署名。

决策：**取料出口不接受 speaker，也不做人工标注、不为此改造 OCR 管线**；字段缺失就照常不吐，**绝不用 `""` 或 `null` 占位**——空署名会被模型读成"此人无名"，比缺失更坏。说话人归属本质是"看画面"的问题（气泡尾指向、角色外观），而 `get_story_context` 已把页码、`reading_order` 与 `boxes` 一并交出，消费侧在生成那一次带图推断即可，无需全库重识别。日后若真要把说话人沉淀成资产，另立 ADR 论证标注成本。

## 影响与收益

- **极速检索体验**：模糊台词查询全库响应稳定在 10ms 以内（本轮改索引侧归一后，真库 6 条查询合计 51ms，含 2 字 LIKE 兜底那条）。**订正**：本条原写"简繁召回率提升至 100%"，按今天的真库复算并不成立——查询侧变体在繁简混排行上有 59% 的漏召回，直到 2026-09-23 的修订（见「决策 2 · 修订」）才把台词出口做到字形无关；
- **全链路资产闭环**：为外围 MCP 服务的 `search_by_dialogue` 工具、飞书搜图/搜梗 Bot 以及后续 Galgame 语料清洗奠定了扎实的数据基石；
- **零安全漏洞**：通过了沙箱越界、访客窥探与幽灵索引等边界用例的严格验证。
