# ADR 0002 — 以图搜图采用 Docker Sidecar + HTTP API 架构

- **日期**：2026-08-22
- **状态**：Accepted

## 背景

随着书库收藏规模达到几千至数万本，用户常有「持有一小块漫画截图/表情包/局部台词框，反查是哪一本哪一页」的强诉求。

技术调研表明：

1. **全局感知哈希（pHash/dHash）** 对裁切、局部缩放的命中率极低，无法满足漫画局部截图检索场景。
2. **通用多模态向量（CLIP/SigLIP）** 体积庞大（几百 MB 到数 GB 模型权重），且在漫画单格局部特写上泛化较差。
3. **`lolishinshi/imsearch`**（基于 ORB 特征点提取 + Faiss/BIVF 聚类索引）针对二次元局部截图具有极高精准度与检索性能（毫秒级）。

但 `imsearch` 采用 **GPL-3.0 许可证**，而纸间（`comic-shelf`）全项目采用 **MIT 许可证** 开源。

## 决策

1. **架构隔离（Sidecar Pattern）**：
   - 将 `imsearch` 作为独立的容器服务（Docker Sidecar，镜像 `aloxaf/imsearch:latest`）运行，通过 HTTP API（如 `http://imsearch:8765`）与纸间 FastAPI 后端通信。
   - 保持网络 IPC 隔离，纸间源码不包含、不链接、不编译任何 GPL-3.0 代码，严格保障纸间项目的 **MIT 开源合规性**。

2. **增量特征索引（Incremental Indexing）**：
   - 遵从纸间「本地优先 + 懒下载」底线。
   - 收录本子时，仅对已缓存的前 4 页封面提取特征并推入索引；正文页面在阅读器懒下载或手动缓存时，触发后台异步增量索引。

3. **优雅降级（Graceful Degradation）**：
   - 后端暴露 `/api/search/image/status` 健康接口。
   - 未启动 `imsearch` 容器时，前端搜索框展示提示引导气泡，常规文字与标签检索 100% 正常工作。

4. **交互形态（Lens Pill & AND Logic）**：
   - 搜索框集成「识图芯片」（微缩图 + 放大预览 + 一键清除 ×）。
   - 支持多模态复合检索（图搜结果 AND 文本/标签过滤）。
   - 书架卡片呈现匹配置信度并支持「直达匹配页阅读器」。

## 后果

- **部署要求**：使用以图搜图功能需额外运行 `imsearch` 容器并分配适当内存（视图片数量，约数百 MB）。
- **解耦优势**：以图搜图模块为可拔插设计，未来可无缝替换为其他轻量或更优的识图引擎，核心业务逻辑零侵入。

## 备选

- **Python 内嵌 OpenCV ORB / pHash**：无需外部容器，但 Python 纯单进程难以承载上万本（数十万页）特征向量的大规模高并发聚类检索。
- **强制集成到后端主容器**：会导致 GPL-3.0 许可证冲突风险，且极大膨胀主后端镜像体积。
