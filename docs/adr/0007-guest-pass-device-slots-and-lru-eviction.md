# ADR 0007 — 访客通行证设备插槽配额、会话凭据与 LRU 淘汰漫游架构

- **日期**：2026-08-30
- **状态**：Accepted
- **关联**：承接并扩展 ADR 0006（动态访客通行证簿与轻量级 SQLite 状态隔离架构）

## 背景

在 ADR 0006 中，系统建立了馆长动态访客簿（Guest Passes）与多租户状态隔离（`user_favorites`、`user_reading_progress`）。但随着实际分享场景的使用，暴露出以下安全性与体验权衡问题：

1. **凭证二次扩散与冒用**：通行证口令（Pass Token）一旦被发送给朋友，若该朋友将口令转发至其他微信群或网络公开平台，任何人拿到该口令均可同时登入使用，系统无法感知到底有几台物理设备接入，也无法阻止扩散；
2. **合法访客多端漫游与网络漂移诉求**：合法访客通常拥有一部主力手机和一台电脑/平板（双持或多持），且在公司、家庭 Wi-Fi、出差高铁蜂窝 5G 之间频繁切换。若采用电商式“一次性激活核销”或“IP 强绑定”，会导致访客换设备无法看书，或网络一切换即被误判封锁掉线；
3. **分发缺乏状态反馈**：馆长在访客簿中无法分辨哪些通行证是“已印发但尚未送出/未激活”，哪些是“朋友已在使用中”，容易导致误将同一通行证重复发放给多位好友，导致数据与借阅冲突。

## 决策

1. **双层凭证与物理设备插槽（Two-Tier Token & Device Slots）**：
   - **通行证口令（Pass Token）**：作为初始门禁钥匙，由馆长派发给朋友；
   - **设备会话凭据（Device Session Token）**：访客在某台设备首次输入通行证口令（或通过免密直达链接 `?token=...` 打开）后，服务端在 SQLite 中持久化该物理设备记录，并向该浏览器写入专属于该设备的 HttpOnly Cookie（`comic_shelf_device`）；
   - 后续日常阅读翻页与喜欢只认该设备的 `device_token`；
   - **IP 脱敏**：鉴权流程与网络 IP 彻底解耦，蜂窝网络与 Wi-Fi 切换 100% 无感，最近访问 IP 仅作为馆长访客簿中的审计与展示线索。
2. **滑动窗口淘汰（LRU Device Eviction）**：
   - 每个通行证拥有设备插槽配额（`max_devices`，默认 2 台，支持馆长在 1~5 台自由微调）；
   - 当第 N+1 台新设备凭通行证口令登入时，系统自动按照 `last_active_at ASC` 将最久未活跃的那台旧设备从数据库注销挤出；
   - 被挤出或被馆长踢除的旧设备在下次请求时收到 401 提示“该设备授权已失效，请重新输入口令”；
   - 此博弈制衡机制保证了合法用户换手机时零沟通自愈，同时一旦口令被外传给多人，偷用者会直接将号主自己的设备顶下线，使二次扩散无法持久共存。
3. **通行证生命周期四态（Pass Activation Lifecycle States）**：
   - 🌿 **待激活（`pending`）**：已印发但设备数为 0，表示尚未被任何人使用，馆长可安心赠予新朋友；
   - 🍃 **使用中（`active`）**：已有至少 1 台设备登入且在配额内（如 `1/2 台设备`）；
   - 🍂 **已满额（`full`）**：绑定设备数达到 `max_devices` 上限；
   - 🛑 **已失效（`expired` / `disabled`）**：已超过到期时间或馆长手动暂停。
4. **防重复发放预警交互（Anti-Duplicate Safeguard）**：
   - 访客簿顶部支持状态胶囊过滤（「全部」·「待激活」·「使用中」·「已失效」），馆长可秒级挑出空白可用卡片；
   - 当馆长点击复制已被设备占用的通行证口令/链接时，弹出琥珀色安全警示：“⚠️ 该通行证已被 X 台设备使用中，再次发送给他人将导致设备互相挤占”，给足操作预期。
5. **馆长端可见度与单端剔除（Curator Telemetry & Device Revocation）**：
   - 馆长在访客簿卡片中可直接查看当前绑定的设备名册（基于 User-Agent 解析的设备类型，如 `iPhone (Safari)`、`macOS (Chrome)`、首次登入时间、最后活跃时间、最近 IP）；
   - 馆长可单独点击 ✕ 精准踢掉某一特定设备（如朋友丢失的旧手机或网吧临时设备），而不影响其他端；重置通行证口令时则自动全量注销所有绑定设备。

## 后果

- **安全性与体验平衡**：通过滑动窗口配额完美兼顾“个人跨端漫游”与“抑制口令群体扩散”，不依赖重型的短信验证码或扫码联动，系统复杂度与运维成本维持在最低点；
- **自愈与低沟通成本**：用户更换新手机或清空浏览器后重新输入口令即可无感顺延，无需向馆长申请解绑；
- **存储扩展**：SQLite 新增 `guest_devices` 表，通过外键级联与 `PRAGMA foreign_keys = ON` 保持轻量高效与数据一致性。
