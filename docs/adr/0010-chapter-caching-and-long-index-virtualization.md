# ADR 0010 — 单话按需离线、章节相对页码契约与长章节目录分批渲染

- **日期**：2026-09-04
- **状态**：Accepted

## 背景

随着纸间引入超长篇连载漫画（如 JM 518074 包含 152 话、7227 页），系统原有的全本预缓存（MAX 600 页）和详情页编排暴露出了三项结构性瓶颈：

1. **缓存轮询空转与资源浪费**：详情页与章节页只要检测到 `cached_pages < page_count`，即使后台无任务（`job.running === false`），也会每秒向后端发起 `api.cacheProgress` 轮询并在前端遍历数千个页面对象，导致 CPU 占用高、网络请求冗余。
2. **全本粗粒度预缓存与超长篇矛盾**：7000 页的长篇漫画用户往往只需要离线阅读接下来的几话，全本缓存既耗尽磁盘又容易触发图床反爬风控；同时每话仅第一页在生成封面时被动缓存，导致用户产生“只有点击封面才缓存”的 bug 错觉。
3. **继续阅读全局页码割裂**：在多章节模式下，若第 3 话起始页为 46，读者读到全局第 47 页（即第 3 话第 2 页），详情页按钮直接显示“继续阅读 · 第 3 話 · 第 47 页”，与单话仅 20 页的实际容量产生视觉冲突。
4. **子章节返回详情页卡顿掉帧**：从子章节（`ChapterView`）返回详情页（`ComicDetailView`）时，组件销毁重载、巨型 JSON 重新传输解析，并瞬间挂载 152 个章节卡片及并发拉取 152 张封面图，严重阻塞主线程并造成 View Transition 掉帧。

## 决策

1. **严格任务驱动轮询（Job-driven Polling）**：
   - 详情页与章节页仅在后台存在明确处于运行态的任务（`job.running === true`）时启动轮询；
   - 页面初始挂载时仅做单次快照拉取，任务结束或组件卸载时立即 `pause()` 暂停轮询。

2. **单话按需离线（Chapter-level Caching）能力闭环**：
   - 后端新增 `POST /api/library/{source}/{source_id}/chapters/{chapter_id}/cache` 与对应进度端点，支持针对单话发起后台多协程下载与缩略图生成；
   - 章节详情页与章节目录卡片提供显式“缓存本话”按钮与精确进度联动，消除缓存机制黑盒。

3. **章节相对页码契约统一（Chapter-relative Page Index）**：
   - 详情页“继续阅读”按钮文案收敛为 `继续阅读 · 第 N 話 · 第 M 页`，其中 `M = global_page - chapter.start + 1`；
   - 气泡提示副标补充 `(全书第 X 页)`，兼顾阅读心智闭合与全局定位精准度。

4. **长章节目录分批增量渲染与内存态 SWR 复用**：
   - `useLibraryStore` 增加内存级 `detailCache`，在章节子路由与父详情页互跳时直接命中内存已有完整元数据对象，杜绝数兆字节 JSON 的二次传输解析；
   - `ChapterIndex` 针对多章节漫画实施分批展开（默认首屏渲染 24 话，提供优雅的增量加载与触底展开机制），将首屏组件数与图片并发限制在安全预算内；
   - 子章节返回按钮优先使用 `router.back()` 保留父视图滚动位点，平滑降级为 `router.replace`。

## 后果

- **正面收益**：
  - 超长篇漫画详情页与子章节间切换实现零白屏、零卡顿、秒级响应；
  - 彻底掐死静默状态下的无意义 HTTP 轮询；
  - 用户拥有针对具体单话离线的自由控制权，大幅降低存储开销与网络封禁风险；
  - 界面页码文案与章节容量完全统一自洽。
- **注意事项**：
  - 章节缓存任务与全本预缓存任务共用后台任务锁，同一本漫画同一时刻只执行一个缓存任务以防磁盘与网络竞态。
