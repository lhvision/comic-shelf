# ADR 0008 — 访客自设 PIN 码认领制、群聊防互挤与全屏零残留门禁架构

- **日期**：2026-09-02
- **状态**：Accepted
- **关联**：承接并升级 ADR 0006（访客簿与 SQLite 状态隔离）与 ADR 0007（设备插槽与 LRU 淘汰）

## 背景

在 ADR 0007 实施后，访客通行证具备了设备插槽配额（默认 2 台）与 LRU 淘汰能力。但在真实分享场景中，出现了两类典型安全与体验挑战：

1. **群聊二次转发与恶性互挤**：馆长将通行证直达链接分发给指定好友后，该好友将链接转发至微信群等公开社群。群内多位用户先后点开链接，由于缺乏身份所有权确权机制，新设备不断将旧设备挤下线，并在 5 分钟内迅速耗尽置换配额触发 10 分钟熔断冷却锁（HTTP 429），导致正常号主与群友全员无法看书；
2. **前端未鉴权状态的 DOM 残留**：在既有单页架构中，未鉴权时应用外壳（`AppHeader`、`RouterView`）仍挂载于 DOM 树底层，仅由前端模态浮层遮罩。若用户在浏览器控制台给遮罩注入 `display: none` 或删除节点，仍能窥探到空骨架或布局结构。

## 决策

1. **读者自设 4~6 位数字 PIN 码认领制（Reader PIN Claiming）**：
   - 通行证新增生命周期状态：`pending`（待认领，未设 PIN）➔ `claimed` / `active`（已认领并绑定设备）；
   - **首次激活（领卡认领）**：首次打开待认领通行证的读者，系统引导其自行设定 4~6 位纯数字 PIN 码（如 `2026`）并确立读者昵称。后端采用 SHA-256 + 独立盐值进行哈希存储（`guest_passes.pin_hash`）；
   - **已认领状态防御**：一旦认领完成，该通行证即被该 PIN 码锁定所有权。任何新设备必须同时出具「有效 Token/直达链接」与「正确的 4~6 位 PIN 码」方可登入。群聊中的未授权路人因无法提供 PIN 码而被 100% 拦截在门外，彻底无法触发设备插槽置换，保护合法号主不被踢下线。

2. **PIN 码防护下的平滑漫游自愈（PIN-Guarded LRU Eviction）**：
   - 当合法号主在自己的新设备（如手机 ➔ 平板/PC）输入正确的 PIN 码成功验证后，若设备插槽已满，系统自动按 LRU 淘汰最久未活跃的旧设备，实现合法号主多端漫游零沟通自愈。

3. **馆长端全流程掌控（Curator Pass Management）**：
   - 馆长访客簿实时呈现认领状态印章：`〔 🌿 待认领 (未设 PIN) 〕` / `〔 🍃 已认领 (已设 PIN) 〕`；
   - 朋友若遗忘 PIN 码，馆长可在卡片上一键执行「重置 PIN 码（清空 PIN 并注销所有已绑设备，重回待认领态）」或「直接代设新 PIN 码」。

4. **全屏零残留门禁（Zero-DOM Gate View）**：
   - 前端根级 `App.vue` 实行严格的 `v-if="!authRequired || authenticated"` 与 `v-else` 两态解耦；
   - 未鉴权时**绝对不挂载** `AppHeader`、`RouterView`、`BackToTop` 及任何业务视图，仅渲染全屏独立的「门禁纸室（`GateView`）」；
   - 即使在 DevTools 控制台强行修改 CSS 或删除门禁节点，页面仅展现纯空白 `<body>`，DOM 树物理级 0 残留，彻底杜绝窥探。

## 后果

- **安全防御闭环**：结合后端 401 拦截、前端 Zero-DOM 物理隔离、Pydantic `^\d{4,6}$` 强正则校验与参数化 SQL 查询，系统在 XSS、SQL 注入与客户端篡改上形成无死角防御；
- **群聊分享鲁棒性**：彻底解决了单张通行证转发群聊引发的频繁互挤与熔断瘫痪问题；
- **多端体验提升**：保留了合法号主在自设 PIN 保护下的无感跨设备平滑顺延体验。
