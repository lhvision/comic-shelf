## 一、推翻了上游设计文档的一个关键处方

那份 2600 行的学习记录给第 3 步开的药方是：两字词用**前缀改写** `喜欢*` 救回倒排。实测在
SQLite 3.46.1 + 本项目 trigram 表上，该处方**完全不成立**：

| 查询式     | 结果 |
| ---------- | ---- |
| `可爱*`    | 0 行 |
| `"可爱"`   | 0 行 |
| `"可爱"*`  | 0 行 |
| `可爱的*`  | 1 行 |
| `可爱啊`   | 1 行 |
| `"太可爱"` | 1 行 |

机理：trigram 只产出**恰好 3 字符**的 token，2 字串产不出任何 token；前缀展开同样要求前缀 ≥3 字。
所以两字词的救法不存在「改写查询」这条低成本路，只有另建 bigram/单字侧表一条路。

## 二、真正对症的是顺序，不是索引

用户原始抱怨是「打两个字搜出来的很难找到想要的」——这是**排序缺失**，不是速度问题（本地库
137 行，`LIKE` 扫描毫无压力）。故本轮不建表、不动索引结构，只给 LIKE 分支补上
`ORDER BY (词频字符量 / max(length(text),1)) DESC, page_index, bubble_id`。

该式即 bm25 中真正参与候选排序的两项：**词频**与**长度归一化**。IDF 对同一次查询是常数，
除掉不改变顺序，故省略。

## 三、因此撤销的抑制，及其代价说明

上一轮为躲「虚假精确」加的 `ranked` 标志 + 非排序路径 `pop("bubble_count")` 已整体删除——
它的前提（候选池是按行号截取的任意 60 行）不复存在：现在两条路径都是先排序再截断，
页级首次出现即该页最优代表句，`bubble_count` 在两条路径上同等可信。

保留的仍是上一条快照立下的**序列化边界**教训：`models.py` 的 `bubble_count` 维持
`int | None = None`，且新增断言要求两条路径的计数都能原样穿过 `response_model`。

## 四、验证

- **反证**：临时摘掉 LIKE 分支的 `ORDER BY`，`test_page_level_aggregation` 立即失败并打印出
  行号序的长句代表句；装回即通过 → 断言有鉴别力，非空转。
- **真实数据**（`jm/1059521`，137 条）：`可爱` 按命中密度排为 `好可爱`(3字) → `毛茸茸的多可爱啊`(8)
  → `毕竟今天的渚超级可爱`(10) → `我也是因为渚太可爱…`(18)；`老师` 让裸两字气泡以密度 1.0 登顶，
  并首次在 2 字路径上报出「3 处命中」。
- 门禁：`bash scripts/test_py.sh` EXIT=0；`pnpm type-check` 0 error；`vp test` Popover 8 passed；
  `vp check` 415 files formatted / 0 lint / 0 type。

## 五、仍欠的债

- 单字查询（如角色名 `渚`）被 `< 2` 字符守卫整条挡掉，返回 0 页。库小其实可放开，但放开等于
  放开全表扫描的口子，与既有不变量冲突，需单独决策。
- 两字词要拿到倒排级别的性能，仍必须建 bigram 侧表——本轮只是证明「不必现在建」。
- 水印被当气泡收录（`jmcomic` / `mcomic`），同时污染检索与第 4 步语料，`min_score` 挡不住。
- 2B（阅读器多气泡高亮）与本条无耦合，但其数据可信度已随本轮一并解除阻塞。
